# サーバーのホスト名・ホスト鍵が変わったときの対応

お名前.com RS では、サーバーの収容替えなどのメンテナンスで、SSH の接続先ホスト名やサーバーのホスト鍵が変わることがあります。
その場合、GitHub Actions のデプロイが失敗するので、Secrets を更新する必要があります。

## 過去の例

- **2026/10/23**: RS プランの一部で収容ホストの変更メンテナンスがあり、IP アドレスとホスト名が変更された。変更前のホスト名は一時的に使えるが、その後利用できなくなる、と案内された（[お知らせ](https://www.onamae.com/news/article/11567)）。

対象になる場合は、お名前.com からメールで案内が届きます。メンテナンスのお知らせが来たら、このドキュメントの手順を予定に入れてください。

## 影響する Secrets

| Secret | ホスト名が変わったとき | ホスト鍵だけが変わったとき |
|---|---|---|
| `SSH_HOST` | **更新する** | そのまま |
| `SSH_KNOWN_HOSTS` | **更新する**（ホスト名が行に含まれるため、鍵が同じでも取り直す） | **更新する** |
| `SSH_PORT` / `SSH_USER` / `DEPLOY_DIR` | 念のため Key 詳細の値と照合する | そのまま |
| `SSH_PRIVATE_KEY` | そのまま（クライアント鍵は変わらない） | そのまま |

## 変更が必要なサイン

| Actions のエラー | 考えられる状況 |
|---|---|
| `Could not resolve hostname` | 古いホスト名が使えなくなった |
| `Connection timed out` / `Connection refused` | 古いホスト名がまだ引けるが、接続先のサーバーが止まっている |
| `Host key verification failed` | 接続先のホスト鍵が `SSH_KNOWN_HOSTS` と一致しない |

## メンテナンス前後の注意

- **メンテナンスの時間帯は FTP / SSH が使えません。** その間に `master` へマージしてもデプロイは失敗するので、マージは避けるか、終わった後に手動実行し直します。
- **収容ホストが変わった後は、古いホストにファイルを置いても新しいホストには引き継がれません。** ホスト名を更新する前にデプロイが成功しても、古いホストに反映されているだけの可能性があります。
- RS のネームサーバー（`ns-rs1.gmoserver.jp` / `ns-rs2.gmoserver.jp`）を使っていれば、IP アドレスの変更に伴う DNS の設定変更は不要です。外部の DNS を使っている場合は、A レコードを新しい IP アドレスに変更します。

## 更新手順

### 1. 新しい接続情報を確認する

コントロールパネル →「サーバー」→「SSH」→ 使用中の Key の「詳細」で、**ホスト名 / ポート番号 / ユーザー名** を確認します。

### 2. 手元から接続して、ホスト鍵を確認する

```powershell
ssh -i $HOME\.ssh\onamae_deploy -p <ポート番号> <ユーザー名>@<新しいホスト名>
```

初回は接続先の指紋を確認するメッセージが出ます。お名前.com の案内どおりの変更であることを確認したうえで `yes` で進め、ログインできることを確認します。

あわせて、デプロイ先のディレクトリが変わっていないことも確認します。

```bash
ls -la ~/public_html/<ドメイン名>
```

### 3. 新しいホスト鍵を取得する

```powershell
ssh-keyscan -p <ポート番号> <新しいホスト名>
```

出力された行をすべて控えます。

### 4. GitHub の Secrets を更新する

Settings → Secrets and variables → Actions で以下を更新します。

- `SSH_HOST` → 新しいホスト名
- `SSH_KNOWN_HOSTS` → 手順3の出力すべて（古い内容は残さず置き換える）
- `SSH_PORT` / `SSH_USER` / `DEPLOY_DIR` → 手順1・2で変わっていた場合のみ

### 5. Actions で確認する

Actions タブから `master` を選んで手動実行（dry-run ON）し、`(DRY RUN)` で正常に終わることを確認します。
新しいホストに初めて同期するときは、全ファイルが転送対象になることがあります（更新日時が異なるため）。問題があるのは、`deleting ...` に消えては困るファイルが出ている場合です。

確認できたら、dry-run を外して手動実行するか、次回の `master` へのマージで本番反映します。

### 6. 手元の known_hosts を整理する（任意）

手元の PC に古いホスト名の記録が残っている場合は削除します。

```powershell
ssh-keygen -R "[<古いホスト名>]:<ポート番号>"
```

## ホスト名が同じなのに `Host key verification failed` になったとき

手元から接続すると `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!` が表示されるはずです。
これは **サーバーのホスト鍵が変わった** か、**接続先がなりすまされている** かのどちらかです。

1. お名前.com のお知らせやメールで、サーバーの変更・メンテナンスの案内があったかを確認する。
2. 案内があった場合のみ、上の手順3〜5（ホスト鍵の取得と `SSH_KNOWN_HOSTS` の更新）を行う。
3. 案内が見当たらない場合は、`SSH_KNOWN_HOSTS` を更新せず、お名前.com のサポートに問い合わせる。

`StrictHostKeyChecking=no` にしてエラーを回避するのは、なりすましを検知できなくなるため行わないでください。
